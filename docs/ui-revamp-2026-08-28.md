## Objective

Rewrite the presentation layer of the feature-complete DPP Analytics application as a coherent, modern business-analytics workspace while preserving routes, API contracts, business definitions and production data behavior.

The result must:

- feel structured rather than like floating dashboard widgets;
- remain comfortable for extended analytical use;
- provide six approved appearances through configuration;
- use shared semantic components and page recipes instead of page-specific visual hardcoding;
- preserve data provenance, metric bases, interpretation rules and Finance invariants;
- work across desktop and mobile;
- be deployed and verified in production with DPP Playwright.

## Approved application structure

### Application shell

- Use a fixed, full-height left sidebar for domain navigation.
- The global header spans the remaining workspace and visually connects to the sidebar. It must not appear as a floating white toolbar.
- The header contains only genuinely global scope, state and actions already supported by the product, plus Appearance. Page-specific windows and filters stay inside their workspace.
- Page title and local tabs live inside the page surface below the global header.
- Use one shell, dimensions and navigation order across every appearance and route.
- The Product Workspace is contextual to Products, not another primary navigation destination.

Primary navigation order:

1. Business
2. Today
3. Sales
4. Products (`/catalog`)
5. Inventory
6. Finance
7. Ads
8. Trajectory
9. Data Health
10. Admin

Keep existing route URLs stable, including `/product?sku=...`.

At mobile widths the sidebar becomes an accessible drawer. Ten destinations must not be compressed into a crowded bottom bar or navigation rail.

### Navigation behavior

The active destination uses more than color:

- stronger type weight;
- a stable inset or background shape;
- a marker or border;
- `aria-current`.

Navigation order and labels remain consistent. The drawer supports keyboard operation, visible focus, Escape dismissal and focus return. Local tabs retain the shared tab semantics and keyboard behavior.

### Surface hierarchy

Use three clear visual levels:

1. **Application chrome:** sidebar and global header.
2. **Page surface:** one continuous working sheet containing page identity, local navigation and content sections.
3. **Bounded objects:** cards only for genuine objects such as a decision, order, product, warning or health result.

Sections such as Overview, Demand and Operations are anchored through alignment, typography, spacing, dividers and shared grid lines. Do not assign unrelated blue, pink or red page regions merely to create separation.

Colored card backgrounds are allowed when they express an intentional component or semantic role. Their visual weight must remain proportional to importance. Basic metadata must not become louder than the analytical evidence it qualifies.

### Content and insight style

- Lead with evidence, not generated-sounding conclusions.
- Do not add loud headers that merely repeat an obvious metric, such as “THE BUSINESS IS GROWING.”
- Keep interpretations concise and adjacent to their inputs, evidence window and rule disclosure.
- Keep metric basis and source labels readable.
- Charts, controls and tables may be polished and dense, but must not add generic BI decoration without a business purpose.

## Design principles

1. Structure establishes hierarchy before color does.
2. Color has defined roles and is never decorative noise.
3. Visual weight follows business importance.
4. Modules belong to a shared grid and page hierarchy; they do not float independently.
5. Long-session readability takes priority over novelty.
6. The same business state has the same meaning in every appearance.
7. Color is never the only status or selection cue.
8. Charts use an independent data palette rather than navigation or severity colors.
9. Responsive behavior follows available width, not user-agent detection.
10. Presentation configuration cannot change business truth.

## Color grammar

The implementation separates these vocabularies:

| Role | Purpose |
| --- | --- |
| Foundation | Canvas, chrome, page surfaces, borders and text |
| Interaction | Links, focus, selected controls and active navigation |
| Brand | DPP identity and restrained accents |
| Data | Chart series, comparisons and analytical categories |
| Semantic status | Healthy, Watch/Warning and Critical states |

Rules:

- Black or dark ink is typography, not severity.
- Blue is not the automatic application or severity color.
- Brand copper or saffron is not automatically a warning.
- Healthy, Watch and Critical use labels and icons or shapes in addition to color.
- Green/red contrasts must remain legible for color-vision differences and never carry meaning alone.
- Positive and negative numbers retain explicit signs and labels.
- Partial or incomplete periods use line, dash, pattern or hatch treatment, not a warning color.
- Section backgrounds remain neutral unless the section itself has a defined semantic role.
- Exact color tokens are finalized only after light/dark contrast and color-vision testing.

## Ergonomics and accessibility

- Default body text: 15–16px.
- Metadata and evidence labels: never below 14px.
- KPI values: generally 24–30px rather than billboard-sized.
- Primary controls: approximately 40–44px high.
- Pointer targets: never below the WCAG 2.2 24px minimum; use 44px where practical.
- Use a clearly visible two-pixel keyboard focus treatment.
- Maintain WCAG AA contrast: 4.5:1 for normal text and 3:1 for large text and meaningful control boundaries.
- Use page-level scrolling. Nested scrolling is limited to genuinely wide charts or tables.
- Wide analytical regions contain their own overflow and must not cause page-level horizontal overflow.
- Long tables use sticky headers where practical.
- Native semantic headings, buttons, tables, captions and ARIA states remain mandatory.
- Motion is restrained and respects reduced-motion preferences.

## Approved appearances

| # | Display name | Technical category | Direction |
| --- | --- | --- | --- |
| 1 | **Warm Studio** | Light theme | Approved warm-neutral reference and default candidate |
| 2 | **Midnight & Saffron / Tinted Signal** | Bold light theme | Stronger color with tinted, not saturated, semantic surfaces |
| 3 | **Aubergine & Aqua / Tinted Signal** | Bold light theme | Distinctive contemporary color with tinted semantic surfaces |
| 4 | **Midnight Dark** | Dark theme | Dark counterpart using the Midnight family |
| 5 | **Aubergine Dark** | Dark theme | Dark counterpart using the Aubergine family |
| 6 | **Weyland** | Visual profile | Dark vector/terminal console treatment |

Terracotta & Teal is explicitly discarded. Mineral, Botanical and Plum & Clay were explorations and are not retained appearances.

The product UI may call all six options “themes.” Technically, Weyland is a profile because it changes more than palette.

### Semantic surface intensity

Keep surface emphasis as a separate configuration axis:

- `quiet`;
- `tinted`;
- `expressive`.

The two approved bold light themes default to `tinted`. The tested saturated yellow and green signal cards were too visually heavy and are not defaults.

### Weyland profile

Weyland may override:

- terminal/monospaced typography;
- blockier and brighter headings, navigation, KPIs and commands;
- lighter mono typography for metadata, axes and telemetry;
- square or chamfered geometry;
- vector-outline controls and charts;
- restrained instrument-panel effects;
- console-style status presentation.

It must avoid dim unreadable green text, continuous flicker, animated scanlines, excessive glow, tiny terminal typography or status syntax that removes the normal readable label. It does not copy fictional-company branding.

Weyland follows the same semantic meanings, accessibility rules, information architecture and route behavior as every other appearance.

## Configurable presentation architecture

Implement presentation through five explicit layers:

1. **Design tokens**  
   Primitive and semantic color, typography, spacing, border, radius, shadow, density, motion and chart tokens.

2. **Semantic components**  
   Examples include application shell, page header, section, metric, decision, chart, evidence table, rule detail, status, product row and empty state.

3. **Page recipes**  
   Define component placement, priority, spans and responsive behavior for overview, evidence, queue, ledger and control-tower compositions.

4. **Shell template**  
   Owns the persistent sidebar, global header, page surface and mobile drawer. Themes cannot replace the approved navigation model.

5. **Appearance profiles**  
   Select theme, density, surface emphasis, typography/geometry profile and restrained effects.

Illustrative contract:

    {
      "schema_version": 1,
      "shell": "persistent-domain-sidebar",
      "theme": "aubergine-aqua",
      "profile": "standard",
      "density": "comfortable",
      "surface_emphasis": "tinted"
    }

Weyland uses `profile: "weyland"` plus its associated palette and component variants.

Configuration is schema-validated, versioned and has a safe Warm Studio fallback. The application supplies the default; a user preference may be stored locally until app-wide user accounts exist. Initial appearance application must avoid a visible flash of the wrong theme.

Templates and themes may control presentation. They may not redefine:

- metric calculations or monetary basis;
- sources, reconciliation or cutoffs;
- inventory or interpretation thresholds;
- lifecycle and taxonomy meaning;
- accessibility semantics;
- stable URL analysis state;
- cache and freshness contracts;
- permissions, Admin authentication or CSRF behavior;
- business behavior.

## Frontend framework decision

The UI revamp retains native HTML, CSS Grid/Flexbox and ES modules.

Visual templating, tokenized appearances, page recipes and shell composition do not materially meet the React decision gate in `docs/frontend-architecture.md`. React/Vite/TypeScript would require a coherent replacement of all 11 served workspace runtimes plus their build, asset-release and QA contracts; isolated islands are not permitted. That migration adds substantial scope and production risk without solving a requirement that the native presentation architecture cannot meet.

React remains available for a future, separately evidenced application-complexity decision.

## Route migration plan

Preserve current API owners, routes, query parameters, browser history, lazy-loading boundaries, session cache behavior and asset-revision contract.

| Block | Workspaces | Critical behavior to preserve |
| --- | --- | --- |
| Foundation | Shared shell, tokens, profiles, components, recipes, Appearance control | One navigation owner, release manifest, immutable asset revision, accessible drawer and focus |
| Reference | Business | Approved hierarchy, decision evidence and shared system calibration |
| Operating and analysis | Today, Sales, Trajectory | Today date/wall mode, URL-restored tabs and filters, lazy Geography, rule traceability |
| Product and evidence | Products/Catalog, Product Workspace | Canonical product identity, URL mode/filter and `sku` context |
| Operations and accounting | Inventory, Finance, Ads, Data Health | Variable action queues, immutable Finance evidence, disconnected Ads lazy loading, health cadence/evidence |
| Administration | Admin | Existing authentication, rate limiting, session, CSRF, optimistic revisions, validation, no-op save and audit behavior |
| Consolidation | All routes | Remove superseded styles, runtimes and selectors; update QA selectors and documentation; no second shell or enhancer layer |

Business, Inventory and Finance are the calibration set for overview, operational queue and dense financial evidence, even though their route delivery may occur in different implementation blocks.

## Pull request and CI strategy

Use significant delivery blocks, not a pull request per theme, route or visual adjustment.

Recommended sequence:

1. **Foundation and Business reference**  
   Artifact and framework decision, six appearances, token/profile engine, shared shell, Appearance selection and Business composition.

2. **Operating and analytical workspaces**  
   Today, Sales and Trajectory, including responsive and URL-state behavior.

3. **Product, operational and accounting workspaces**  
   Products/Catalog, Product Workspace, Inventory, Finance, Ads, Data Health and Admin.

4. **Consolidation and audit hardening**  
   Legacy removal, complete responsive/accessibility hardening, final production audit and documentation reconciliation.

Keep work local until each block is coherent. Push meaningful milestones rather than triggering CI for every small visual edit. Existing required path-scoped Application quality jobs remain authoritative and are not bypassed.

For each block:

- run targeted lint and tests during development;
- run the relevant local application-quality and browser syntax gates before opening the PR;
- open one PR referencing tracker #206 and its completed tasks;
- merge only when the block is internally complete;
- allow the normal `main` deployment to run;
- verify the exact deployed SHA and asset revision in production;
- use DPP Playwright for production desktop and mobile navigation and visual review;
- record evidence on the tracker before beginning the next block.

Do not manually dispatch duplicate full CI/deployment chains when the push or merge workflow already supplies the required result.

## QA strategy

### Per implementation block

- Shared frontend contract and formatting/lint gates.
- Board Python/image tests when packaging or server ownership changes.
- QA script syntax for changed browser tests.
- Targeted accessibility and keyboard smoke.
- Changed-route desktop/mobile screenshots.
- Console, failed-response and horizontal-overflow checks.
- Direct-load, refresh and Back/Forward checks for affected URL state.
- Before/after API and rendered-number comparison for affected pages.

### Appearance validation

Avoid multiplying every PR into a full route × appearance × viewport matrix.

During development:

- test the complete six-appearance matrix against a component/state gallery;
- test Business, Inventory and Finance in all six appearances at desktop and mobile widths;
- smoke every route in Warm Studio, one dark theme and Weyland;
- test warning, critical, healthy, empty, loading, partial-period, long-label and all-zero chart states.

At final acceptance, broaden coverage based on component and route risk rather than duplicating identical screenshots.

### Production validation

Post-deploy UI-revamp acceptance uses the standalone, parameterized DPP Playwright runner, not the desktop-only
CI integration. Run Chromium desktop, Chromium with the Pixel 5 device, WebKit desktop, and WebKit with the
iPhone 12 device. Begin each run by recording the exact deployed SHA from the footer and the active asset
revision.

The standalone DPP Playwright runner verifies:

- every primary route and the contextual Product route;
- sidebar navigation and active state;
- mobile drawer behavior;
- direct URLs and browser history;
- all Appearance choices and preference restoration;
- chart/table overflow containment;
- no application-owned console errors or failed responses;
- exact deployed SHA and asset revision;
- no unexpected business-value or basis changes.

Production, not a local mock, is the final visual source of truth.

## Risks and controls

| Risk | Control |
| --- | --- |
| Theme-specific hardcoded colors leak into pages | Semantic tokens, lint/contract checks and component-state gallery |
| A visual rewrite changes business meaning | Preserve APIs/view models; compare payloads and rendered numbers |
| A second frontend system appears | Retain the approved native architecture and one owner per layer |
| Six appearances create unbounded QA cost | Component matrix plus risk-based route sampling and full default-navigation gate |
| Dark/Weyland modes reduce legibility | Contrast, focus, color-vision and dim-text checks |
| Bold signal cards overpower evidence | Tinted default, semantic surfaces only and weight review on calibration pages |
| Route migration breaks saved views | Preserve and test query keys, refresh and Back/Forward |
| Mobile layouts overflow or become too dense | Phone-width visual QA and contained table/chart scrolling |
| New assets regress load performance | Preserve lazy detail/chart boundaries and inspect resource payloads |
| Cached mixed releases show old styling | Preserve `asset_release.py` manifest and production revision QA |
| Admin redesign weakens security or workflow | Preserve server-owned auth, CSRF, revisions and Admin QA |
| QA selectors bind to incidental styling | Use stable semantic markers and update selectors in the same PR |

## Definition of done

The revamp is complete only when:

- all six approved appearances are selectable and restore safely;
- Warm Studio is the documented fallback/default candidate;
- the two bold light themes use tinted semantic surfaces by default;
- Weyland has its approved blocky/brighter hierarchy without sacrificing readability;
- all primary routes use the persistent sidebar and connected global header;
- all routes retain their existing URLs, APIs and stable analytical state;
- each workspace has one clear composition, style and runtime owner;
- presentation is driven by tokens, components, recipes and profiles rather than page palette hardcoding;
- no appearance changes business semantics or accessibility structure;
- supported desktop/mobile widths avoid page-level horizontal overflow;
- keyboard, focus, target-size and WCAG AA contrast checks pass;
- existing cache, lazy-load, asset revision, Finance, metric-basis and interpretation-rule tests remain green;
- DPP Playwright completes production navigation and visual verification on the exact deployed SHA;
- production has no application-owned console or failed-response errors;
- documentation and QA selectors match the final architecture;
- superseded frontend layers are removed rather than retained as overrides;
- tracker #206 contains repeatable production evidence for every completed block.
